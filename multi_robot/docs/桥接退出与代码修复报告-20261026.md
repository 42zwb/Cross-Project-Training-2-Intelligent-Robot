# 桥接退出与代码核查修复（2026-10-26）

本报告接续同日的随机场景预览，重点处理此前真实复现的 `free(): corrupted unsorted chunks`。旧报告中的失败记录保留为历史证据；当前修复和复验以本报告为准。代码交付分支仍为 `preview/seeded-scenes-15m`。

## 1. 桥接退出缺陷

环境：Ubuntu 22.04、ROS 2 Humble、Gazebo Fortress，系统 `ros_gz_bridge 0.244.26`、`rclcpp 16.0.21`、`tf2 0.25.23`。桥接进程不链接本工程的 tf2 库，本次没有替换系统 ROS/Gazebo 库，也没有使用 `LD_PRELOAD` 绕过异常。

### 证据与定位

1. 从此前 robot2 雷达桥的真实 core 中恢复 GDB 堆栈，确认崩溃点是进程退出时的 `__run_exit_handlers → free → _int_free → malloc_printerr`。当时 DDS、Gazebo transport 和 ROS 延迟信号处理线程仍存在。
2. 对照安装版本的源码，确认节点持有桥接句柄、句柄又强引用节点，ROS 订阅回调还会持有节点，形成循环引用；原入口 `spin()` 返回后直接返回主函数，没有显式完成 ROS 信号处理器的退出。
3. 独立原生探针对 GZ→ROS、ROS→GZ、双向三种桥接各测三次：原所有权模型释放外部引用后仍保留 **9/9** 个节点；修复后保留 **0/9**，重复调用清理也通过。
4. 在 GDB 的进程 `exit()` 断点直接比较真实入口：旧入口仍有 DDS 和 ROS 信号处理线程堆栈；新入口两者均已消失。独立探针同时确认原入口退出路径的 ROS 信号处理器仍安装，新入口已卸载。两组探针的延迟 shutdown 回调都完成，不能将该回调本身作为差异证据。

上游也分别修复过这些所有权和退出问题，见 [PR 952](https://github.com/gazebosim/ros_gz/pull/952)、[PR 977](https://github.com/gazebosim/ros_gz/pull/977)。本项目针对已安装 Humble API 实现兼容入口，没有直接混装其他发行版二进制。

### 实际修改

新增原生包 [`fleet_bridge`](../src/fleet_bridge/UPSTREAM.md)，多机器人 launch 中的时钟和三个雷达桥都使用它。消息工厂及转换继续调用安装版本的 `libros_gz_bridge.so`。

- `spin()` 返回及错误分支均显式调用 `rclcpp::shutdown()`，完成信号处理线程退出。
- 在工厂对象释放前，取消心跳并退订 Gazebo 输入，避免回调继续引用工厂的裸指针；随后释放服务、句柄与 transport 引用，打断节点循环引用。
- 保留监督脚本的停车、关闭数据源和异常退出检查；修复节点自身生命周期后，再以实际退出结果验收。
- 缺方向、缺消息类型、不支持的主题或服务映射现在立即非零返回，避免配置错误时进程一直存在却没有工作桥接。
- `run.sh` 检查新入口是否已构建，旧工作空间更新后可自动补建。

这是已经定位并修复的生命周期缺陷。历史 core 只保留了堆分配器发现损坏的位置，**尚未捕获第一次写坏堆内存的指令**；因此不将上述证据扩大为“所有可能的内存错误均已排除”。

地图融合只读取真实输入栅格，未知没有被强制改为空闲，障碍优先级继续保留。单机器人源码本轮未改动，重新执行其全部测试。

### 配置边界

另外尝试种子 42、robot1 初始朝向 0.6 rad / robot3 −0.4 rad，分辨率分别为 0.025 m 和 0.05 m。两轮传感、TF、导航均启动，但机器人起点附近真实输入地图仍有窄条未知观测，robot1 安全空闲净空约 **0.18 m**，小于要求的 **0.28 m**，因此保持 BOOTSTRAP、拒绝运动，两轮退出均正常。这两轮**不计作导航通过**。

已增加明确的等待原因；没有把未知栅格填白，也没有擅自执行开机旋转。默认朝向 0、分辨率 0.05 m 的配置已在最终流程验证就绪及实际探索。其他朝向、分辨率、种子或长时间耐久仍需要各自运行验证；本轮没有重新完成随机场景三种队形的全部流程。
